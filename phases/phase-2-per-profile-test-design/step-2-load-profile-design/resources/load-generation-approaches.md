# Resource: Load Generation Approaches

## UI-Driven Load Generation

Load generated by driving the actual UI (browser automation). Most realistic for end-to-end user experience (captures client-side rendering), but resource-intensive per virtual user, limiting concurrent scale. Relevant when acceptance criteria include client-perceived response time.

## API / Protocol-Level Load Generation

Load generated directly against the API/protocol layer without rendering UI. Most common approach — isolates backend performance from client rendering variability, scales to far higher concurrent VU counts. Most transaction-level acceptance criteria assume this approach.

## Crowd / Real-Device Load Generation

Load from geographically distributed real devices/browsers. Useful when network variability and real-world client diversity is itself part of what's tested (e.g., a CDN's global performance).

## Why This Matters for Load Profile Design

Acceptance criteria must specify **where** response time is measured (client-side vs. server-side at the API boundary) — a direct consequence of the assumed load generation approach. State this explicitly whenever it isn't obvious, so Step 4's script blueprint knows where the measurement point belongs.
