# Resource: Operational Profile Types Reference

Use this as a completeness check after Profile Boundary Definition — walk the discovered profile list against these categories and confirm nothing was missed. Not every system has every category; the point is to deliberately confirm absence rather than silently overlook it.

## Customer / End-User Facing Profiles

The most commonly discovered category — human users directly interacting with the system's primary function. Often splits into sub-categories worth checking separately: authenticated vs. unauthenticated users, different subscription/service tiers, different channels (web vs. mobile vs. API-driven third-party clients using the same backend).

## Backoffice / Administrative Profiles

Internal staff using the system to manage, moderate, approve, or support the customer-facing function. Frequently under-prioritized because volume is low relative to customer-facing traffic — but often business-critical (see Profile Prioritization's fulfillment-approval example) and frequently under-tested in practice precisely because of that volume bias, which is worth actively correcting for.

## System-to-System / Integration Profiles

Traffic generated by other systems calling into this one (partner APIs, upstream services, webhooks received) or by this system calling out. These are secondary-actor-driven profiles per System Document Analysis's actor classification, and usually follow a closed or semi-closed workload model rather than the open model typical of human traffic (see Phase 2 Step 3's Open vs. Closed Model technique).

## Scheduled / Batch Profiles

Time-triggered rather than actor-triggered activity: nightly reconciliation jobs, report generation, data archival, cache warming. Worth identifying separately because their "load" isn't measured in concurrent users at all, but in data volume and processing-window duration — this affects which techniques in Phase 2 apply (Volume Testing is far more often relevant here than to human-driven profiles).

## Event-Driven / Reactive Profiles

Triggered by external events outside the system's own schedule or direct user action — e.g., a spike in traffic caused by a marketing email send, a price-drop notification fan-out, or an IoT device burst. Often overlaps with Spike Testing needs identified later in Phase 2 Step 2, but the _profile_ itself (who/what generates this traffic, in what pattern) still needs to be identified here in Phase 1 rather than assumed away as "just part of" a related customer-facing profile.

## Why This Belongs in Phase 1

A profile list that only contains customer-facing profiles because that's what the FRD emphasized is an incomplete discovery — this reference exists to catch that bias before Human Review Gate 1, not after Phase 2 has already been run for an incomplete list.
