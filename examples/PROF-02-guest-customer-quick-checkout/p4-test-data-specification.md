No `session_token`/login correlation exists in this profile (no account, per profile scope) — this is the most structurally significant correlation-map difference from PROF-01, and is stated explicitly rather than left as a silent gap.

## 3. Data Diversity Rules

Same `product_id` and `search_term` diversity treatment as PROF-01 (shared catalog, shared placeholder weighting, same flagged need for real distribution data). No new diversity concerns specific to this profile's guest-only fields (`guest_session_id` and `guest_payment_card_details` are both fresh/cycled with no cache-sensitivity).

## 4. Script Blueprint Specification

### Initialization

No authentication step (no account). Generate a fresh `guest_session_id` for this iteration.

### Main Flow

1. Browse Catalog
2. Search
3. Add to Cart (captures `cart_id`)
4. **Decision point:** `[ASSUMPTION - 6% of iterations continue to checkout, per Step 3's lower guest-conversion estimate]`; remainder end here
5. _(For the ~6% proceeding)_ Select Delivery Slot (captures `delivery_slot_reservation_id`)
6. Enter Payment Details (manual card entry — this step has no analog in PROF-01's flow)
7. Confirm Payment (injects `cart_id`; captures `payment_authorization_id`)
8. Submit Order (injects `delivery_slot_reservation_id`, `payment_authorization_id`; captures `order_id`)

### Verification Points

Same pattern as PROF-01: Confirm Payment requires `authorization.status == "approved"`, not just HTTP 200; Submit Order requires `order.id` present.

### Error Handling

Same no-retry policy as PROF-01 for Confirm Payment and Submit Order, for the same duplicate-charge/duplicate-order reasons — this is a property of the shared Order Service code path, not something that would differ by profile.

### Cleanup/Termination

None required.
