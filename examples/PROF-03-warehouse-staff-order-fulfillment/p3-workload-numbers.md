**Pacing calculation (per picker, one full picking-list cycle, not one Item Scan alone):** This profile's meaningful "iteration" unit is a full picking-list cycle (List Retrieval → N Item Scans → Pack Confirmation), not a single Item Scan — since Item Scan's own high-frequency repetition within a cycle is exactly what Step 1 flagged as this profile's dominant characteristic. `[ASSUMPTION]` Estimated average items-per-order ≈ 12 (a typical grocery basket size), so one full cycle ≈ List Retrieval (2s) + 12 × (scan 300ms + 65s handling) + Pack Confirmation (estimated 500ms + 120s handling) ≈ 2 + 12×65.3 + 120.5 ≈ **906.1s (~15.1 minutes) per full picking cycle per picker.**

## 3. Little's Law Application — Concurrency Derived Directly from Staffing, Not Calculated

Since this is a closed, population-limited model, **N is not calculated via Little's Law from a throughput target — N is the staffing level itself**, directly, per the technique's own explicit guidance that "for these, the worker pool size _is_ N already, defined directly."

**N = 75 concurrent active Pickers/Packers (from Step 1's estimated staffing figure, itself flagged as an assumption pending real WMS headcount data) + 5 concurrent Dispatchers = 80 total concurrent actors for this profile.**

No safety margin is applied to a staffing-derived N in the same way as an arrival-rate-derived N — adding an artificial "safety margin" to a headcount figure would misrepresent it as if it were uncertain in the same way a calculated throughput figure is; the actual uncertainty here (whether 75/5 are the right headcount estimates at all) is already flagged as `[ASSUMPTION]` at the source, which is the more honest way to represent this particular uncertainty than inflating the number itself.

**Cross-check via N = λ × W (informational only, not how N was derived):** implied λ = N / W = 75 / 906.1s ≈ 0.0828 cycles/sec ≈ 298 cycles/hr system-wide (Pickers only) — multiplying by the ~12 items/cycle estimate gives ≈3,576 Item Scans/hr, reasonably close to Step 1's independently-estimated 4,000/hr (both figures share the same underlying 55-scans/hr-per-picker assumption, so this is a consistency check on arithmetic, not an independent validation of the assumption itself — worth stating plainly rather than overclaiming what the cross-check actually proves).
